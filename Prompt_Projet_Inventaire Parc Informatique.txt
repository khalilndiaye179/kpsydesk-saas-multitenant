OBJECTIF

Transformer cette application existante en plateforme SaaS multi-tenant 
permettant à plusieurs entreprises indépendantes de s'inscrire, chacune 
disposant d'un espace de gestion et de stockage de données totalement 
isolé des autres, sans dupliquer l'infrastructure par client, et SANS 
CASSER les fonctionnalités déjà en place.

CONTRAINTE DE PORTS

Tous les services (backend NestJS, frontend Vite/dev-server, éventuel 
service annexe comme un adminer/pgAdmin de dev) doivent utiliser 
exclusivement des ports compris entre 3010 et 3015. Mets à jour en 
conséquence :
- docker-compose.yml (mapping des ports)
- les fichiers .env / .env.example
- la configuration Vite (vite.config.ts)
- la configuration CORS du backend NestJS
- toute documentation ou script de démarrage existant

Répartis les ports de façon claire, par exemple :
- 3010 : backend NestJS (API)
- 3011 : frontend (dev server Vite)
- 3012 : PostgreSQL (si exposé en dev)
- 3013-3015 : réservés pour services futurs (ex: worker de facturation, 
  service de notifications)

Documente cette répartition dans un fichier PORTS.md à la racine du projet.

STRATÉGIE D'ISOLATION DEMANDÉE

Utiliser l'approche "shared database, shared schema, tenant discriminator" :
- Une seule base PostgreSQL (celle déjà en place)
- Une colonne `tenantId` (UUID) ajoutée à toutes les tables métier existantes 
  du schema.prisma actuel
- Isolation garantie via un middleware/extension Prisma qui injecte et 
  filtre automatiquement `tenantId` sur TOUTES les opérations (findMany, 
  findUnique, create, update, delete, count) pour empêcher toute fuite 
  de données inter-entreprises
- En complément, active Row Level Security (RLS) au niveau PostgreSQL 
  comme filet de sécurité indépendant du code applicatif

TÂCHES ATTENDUES (dans cet ordre, avec validation entre chaque étape)

1. SCHÉMA PRISMA
   - Créer un modèle `Tenant` (id, nom, sousDomaine, statut, dateCreation, 
     planId)
   - Créer un modèle `Subscription` (tenantId, plan, statut, dateDebut, 
     dateFin, quotaActifs)
   - Créer un modèle `Plan` (nom, prix, quotaActifs, quotaUtilisateurs, 
     fonctionnalitesIncluses)
   - Ajouter `tenantId` (relation vers Tenant) sur tous les modèles métier 
     existants du schema.prisma actuel (Equipement, Licence, Ticket, 
     Utilisateur, etc.)
   - Créer la migration Prisma correspondante, avec un script de backfill 
     qui assigne un tenant "legacy" par défaut aux données déjà présentes 
     en base avant de rendre tenantId NOT NULL

2. BACKEND NESTJS
   - Créer un `TenantModule` avec un `TenantMiddleware` qui résout le 
     tenant actif à partir du sous-domaine de la requête (ex: 
     entreprise-x.inventaire-parc.com) ou d'un header `X-Tenant-ID` en 
     environnement de dev
   - Créer un `TenantGuard` qui vérifie que l'utilisateur JWT appartient 
     bien au tenant résolu
   - Modifier le payload JWT pour y inclure `tenantId`
   - Créer une extension Prisma avec AsyncLocalStorage qui filtre 
     automatiquement toutes les requêtes par `tenantId` du contexte courant
   - Créer un `TenantsController` avec endpoint d'inscription publique 
     (POST /signup) : création du tenant + compte administrateur initial + 
     envoi d'email de confirmation
   - Créer un `SubscriptionsController` pour la gestion des abonnements 
     (souscription, changement de plan, annulation)
   - Ajouter un `QuotaGuard` qui bloque la création de ressources si le 
     quota du plan souscrit est dépassé

3. FRONTEND REACT
   - Créer une page publique `/signup` (formulaire d'inscription entreprise : 
     nom entreprise, sous-domaine souhaité, email admin, mot de passe, 
     choix du plan)
   - Créer une page `/pricing` présentant les différents plans
   - Adapter le contexte d'authentification pour stocker et transmettre le 
     `tenantId` dans les appels API
   - Créer un espace "Mon abonnement" dans le dashboard existant (plan 
     actuel, quota utilisé, upgrade/downgrade)

4. SÉCURITÉ
   - Écrire des tests d'intégration prouvant qu'un utilisateur du Tenant A 
     ne peut JAMAIS lire, modifier ou supprimer une donnée du Tenant B, 
     même en manipulant les IDs dans les requêtes API
   - Ajouter un rate limiting par tenant (éviter qu'un client sature 
     l'infra partagée)

5. DOCKER & PORTS
   - Adapter le docker-compose.yml pour ce fonctionnement multi-tenant 
     mutualisé (pas d'instance par client), avec les ports 3010-3015
   - Documenter les variables d'environnement nécessaires
   - Créer le fichier PORTS.md documentant la répartition des ports
